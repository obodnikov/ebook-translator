# book-translator

> Программа командной строки (CLI) для перевода книг в формате EPUB с английского
> на русский через любой OpenAI-совместимый API (OpenRouter, kiro-gateway, локальные
> модели). Сохраняет оформление и вёрстку книги, ведёт словарь терминов на уровне
> книги и серии для единообразия имён, кэширует переводы на уровне фрагмента.

Статус: версия 0.4. Работает от начала до конца с полным конвейером качества
(`glossary → promote → translate → judge → reflect → proofread → style → verify → assemble с reader notes`).
Оператор ведёт процесс вручную. Подробности — в [`IMPLEMENTATION_PLAN.md`](IMPLEMENTATION_PLAN.md).

## Требования

- Python 3.12 или новее
- `uv` или `pip`
- Доступ к OpenAI-совместимому API — OpenRouter, kiro-gateway, llama.cpp,
  vLLM, или любой другой endpoint с `/v1/chat/completions`.
- Для перевода обложки — провайдер с поддержкой image generation
  (OpenRouter + модели Gemini/GPT с генерацией изображений).
- Файл EPUB (расшифрованный, без защиты от копирования (DRM)).

По желанию: Calibre или Apple Books для просмотра готового EPUB.

## Установка

```bash
git clone <repo> ebook-translator
cd ebook-translator

# Виртуальное окружение Python (один раз)
python3.12 -m venv .venv
source .venv/bin/activate

# Пакет и зависимости
pip install -e .

# Конфигурация
cp .env.example .env
# Положить в .env нужные ключи (см. раздел «Провайдеры»)
```

После установки в виртуальном окружении появится команда `btrans`. Далее
во всех примерах предполагается, что окружение активировано
(или вызов через полный путь `.venv/bin/btrans`).

## Провайдеры (LLM endpoints)

Система маршрутизирует запросы по **провайдерам**. Базовых два:

- **`text`** — дефолт для всех текстовых стадий (словарь, перевод, оценка,
  рефлексия, корректура, стилистика, сверка).
- **`image`** — генерация изображений (перевод обложки).

Дополнительно **любую текстовую стадию можно увести на отдельный провайдер**
через одноимённый оверрайд (см. «Оверрайды по стадиям»). Каждый провайдер —
любой OpenAI-совместимый endpoint.

### Зачем разделять провайдеры?

Текстовые задачи и генерация изображений — разные возможности, и не каждый
endpoint умеет оба. Кроме того, у провайдеров разные лимиты контекста:

- **kiro-gateway** — отлично для текстовых моделей Claude, но не поддерживает
  генерацию изображений, **ограничивает длину ответа** (см. «Ограничение шлюза
  на длину ответа») и **режет очень большой вход** (важно для глоссария — см.
  ниже).
- **OpenRouter** — поддерживает всё, контекст до 200k токенов, но платный.
- **vLLM / llama.cpp** — локальные модели для текста, без image.

Маршрутизация по стадиям позволяет направить каждую задачу к подходящему
провайдеру.

### Конфигурация

В `configs/default.yaml`:

```yaml
providers:
  text:
    base_url: "http://localhost:9000/v1"    # дефолт для всех текстовых стадий
    api_key_env: "KIRO_GATEWAY_API_KEY"     # имя переменной окружения с ключом
  image:
    base_url: "https://openrouter.ai/api/v1"  # генерация обложки
    api_key_env: "OPENROUTER_API_KEY"
```

В `.env`:

```bash
KIRO_GATEWAY_API_KEY=my-super-secret-password-123
OPENROUTER_API_KEY=sk-or-v1-...
```

### Оверрайды по стадиям

Помимо `text` и `image`, в секции `providers` можно задать оверрайд для
**любой текстовой стадии**. Не задан — стадия идёт на `text`. Доступные ключи:

| Ключ | Стадия |
|------|--------|
| `text` | дефолт для всех текстовых стадий |
| `image` | генерация обложки |
| `glossary` | извлечение словаря |
| `translate` | перевод |
| `judge` | оценка |
| `reflect` | рефлексия |
| `proofread` | корректура |
| `style` | стилистика |
| `verify` | сверка |
| `repair` | починка замечаний оценщика |

> ⚠️ Имя стадии должно **совпадать точно**. Незнакомые ключи в `providers`
> молча игнорируются (стадия тихо уйдёт на `text`) — сверяйтесь с таблицей.

Пример: текст и все стадии через kiro-gateway, а словарь и обложку — на
OpenRouter:

```yaml
providers:
  text:                       # дефолт всех текстовых стадий (перевод, judge, ...)
    base_url: "http://localhost:9000/v1"
    api_key_env: "KIRO_GATEWAY_API_KEY"
  glossary:                   # оверрайд: словарь шлёт всю книгу — нужен большой контекст
    base_url: "https://openrouter.ai/api/v1"
    api_key_env: "OPENROUTER_API_KEY"
  image:
    base_url: "https://openrouter.ai/api/v1"
    api_key_env: "OPENROUTER_API_KEY"
```

Готовый пример: `configs/kiro-gateway.yaml.example`. Скопировать в
`configs/default.yaml` или указать через `--config путь`.

### Почему глоссарий стоит увести на OpenRouter

Извлечение словаря — единственная стадия, которая отправляет **всю книгу
одним запросом** (~150k токенов для романа на ~110k слов). Остальные стадии
работают по фрагментам и в окно любого провайдера помещаются.

Через kiro-gateway эта стадия не проходит по двум причинам сразу.

**Ответ обрывается.** Словарь отдаёт список на сотню статей. При проверке ответ
оборвался на 26 825 байтах посреди JSON, не дойдя до конца, — у шлюза жёсткое
ограничение на длину ответа (см. «Ограничение шлюза на длину ответа»).

**Вход может быть урезан.** Шлюз режет очень большой вход, и словарь тогда молча
покрывал бы только начало книги. Чтобы этого не случилось, стадия `glossary`
проверяет служебные метки в начале и конце текста и **громко падает с ошибкой**
(`TruncationError`), а не пишет неполный словарь.

Поэтому при `text: kiro-gateway` глоссарий уводится на OpenRouter (контекст
200k — типовой роман помещается целиком). Стадии, работающие по фрагментам,
при этом спокойно остаются на шлюзе.

### Ограничение шлюза на длину ответа

У kiro-gateway есть предел на **длину ответа** (не запроса), и это главное, что
нужно учитывать при его использовании. Замеры на реальной книге:

- запросы проходят как минимум до 331 КБ — со стороны входа ограничения не видно;
- полный ответ на 23 644 байта приходил целиком, ответ на 26 825 байт обрывался
  посреди JSON;
- судя по разнице между русским текстом и английским JSON, предел считается
  в токенах, а не в байтах. Для русского он наступает раньше: кириллица занимает
  два байта на знак.

**Шлюз об обрыве не сообщает.** Поле `finish_reason` приходит со значением
`stop` даже когда ответ пустой. Поэтому в настройках провайдера задаётся
`max_response_bytes` — осторожная граница, при приближении к которой программа
пишет предупреждение в журнал. Это единственный доступный ранний признак.

```yaml
providers:
  text:
    base_url: "http://localhost:9000/v1"
    api_key_env: "KIRO_GATEWAY_API_KEY"
    max_response_bytes: 24000    # порог предупреждения, не точный предел
```

Если ответ всё же придёт пустым, программа остановится с внятной ошибкой и
**не запишет пустоту в кэш**. Повторять такой запрос бесполезно, поэтому
повторных попыток не делается.

Из-за этого предела в конфигурации для шлюза размер фрагмента уменьшен:
`chunker.target_words: 1200` вместо 2000. При 2000 словах перевод занимал до
99,9% предела — запаса не оставалось. При 1200 самый крупный фрагмент книги дал
14 224 байта, около 60%. В конфигурации под OpenRouter остаются прежние 2000:
там такого ограничения нет.

> **Менять размер фрагмента задним числом дорого.** Сдвигаются границы
> фрагментов, и весь накопленный перевод в кэше обесценивается. Выберите
> значение один раз.

### Обязательное условие: `FAKE_REASONING=false`

В настройках самого шлюза размышление модели должно быть выключено.

У Kiro нет отдельного канала для размышлений, поэтому шлюз их подделывает:
подмешивает в запрос служебные метки и вырезает из ответа помеченный кусок.
Размышление при этом расходует **тот же бюджет ответа**, что и сам текст. На
переводе оно съедает бюджет целиком, и ответ приходит пустым — проверено и при
2000, и при 1200 слов во фрагменте.

Параметр `reasoning_effort` от этого не спасает: он отменяет вставку служебных
меток, но разбор ответа продолжает работать, пока включён общий выключатель.
Спасает только `FAKE_REASONING=false`.

Обратная сторона: **на шлюзе размышления нет вовсе**. Стадии, которым оно
помогает, уводятся на OpenRouter — см. таблицу ниже.

### Какой провайдер для какой стадии рекомендуется

Раскладка получена замерами на реальной книге, а не выбрана произвольно.
Правило простое: на бесплатном шлюзе — то, что даёт длинный ответ и не выигрывает
от размышления; на платном OpenRouter — то, что отвечает коротко и от размышления
выигрывает. Дорогая по объёму работа остаётся бесплатной.

| Стадия | Провайдер | Почему |
|--------|-----------|--------|
| `translate` | шлюз | наибольший объём ответа, размышление не нужно |
| `style` | шлюз | с размышлением и без него правки совпали дословно |
| `verify` | шлюз | то же |
| `reflect` | шлюз | по форме это тот же перевод |
| `glossary` | OpenRouter | на шлюзе ответ обрывается |
| `judge` | OpenRouter | ответ около 1,5 КБ, значит дёшево; размышление нужно |
| `proofread` | OpenRouter | правки мелкие, значит дёшево; размышление нужно |
| `repair` | OpenRouter | ответ — короткий список «принять/отклонить»; размышление нужно |

Готовый пример такой раскладки — [`configs/kiro-gateway.yaml.example`](configs/kiro-gateway.yaml.example).

Оценка расходов: на OpenRouter уходят только стадии с коротким ответом. Полный
проход оценщика по роману обошёлся примерно в два доллара.

### Соответствие команд и ключей конфигурации

| Команда | Ключ конфига (дефолт — `text`) |
|---------|--------------------------------|
| `btrans glossary extract` | `glossary` → иначе `text` |
| `btrans translate` | `translate` → иначе `text` |
| `btrans judge` | `judge` → иначе `text` |
| `btrans reflect` | `reflect` → иначе `text` |
| `btrans proofread` | `proofread` → иначе `text` |
| `btrans style` | `style` → иначе `text` |
| `btrans verify` | `verify` → иначе `text` |
| `btrans repair` | `repair` → иначе `text` |
| `btrans translate --cover` | **`image`** (opt-in) |
| `btrans cover translate` | **`image`** |
| `btrans cover replace` / `extract` | — (не вызывает LLM) |

### Дополнительные параметры

Каждый провайдер поддерживает `extra_headers` для кастомных заголовков:

```yaml
providers:
  text:
    base_url: "https://openrouter.ai/api/v1"
    api_key_env: "OPENROUTER_API_KEY"
    extra_headers:
      HTTP-Referer: "https://my-app.example.com"
      X-OpenRouter-Title: "book-translator"
```

### Совместимость

Если секция `providers` не указана в конфиге — используются значения по
умолчанию: оба провайдера → OpenRouter, ключ из `OPENROUTER_API_KEY`.
Старые конфиги без `providers` работают без изменений.

### Имена моделей

Имена моделей задаются в секции `models:` и должны соответствовать **тому
провайдеру, на который уходит стадия**. Нормализации имён нет — строка из
конфига уходит провайдеру дословно. Формат:

- **OpenRouter:** с префиксом — `anthropic/claude-sonnet-4.6`,
  `google/gemini-3.1-flash-image-preview`
- **kiro-gateway:** короткое имя без префикса — `claude-sonnet-4.6`,
  `claude-haiku-4.5`
- **vLLM / llama.cpp:** имя модели как указано при запуске сервера

Если стадия уведена оверрайдом на другой провайдер — соответствующая модель в
`models:` должна быть в формате этого провайдера. Пример: `glossary` →
OpenRouter, остальное → kiro-gateway:

```yaml
models:
  glossary:   anthropic/claude-sonnet-4.6   # OpenRouter — с префиксом
  translate:  claude-sonnet-4.6             # kiro-gateway — без префикса
  judge:      claude-haiku-4.5
  reflect:    claude-sonnet-4.6
  proofread:  claude-haiku-4.5
  style:      claude-sonnet-4.6
  verify:     claude-sonnet-4.6
```

## Перевод книги: пошагово

Рабочий пример — книга 4 из серии «Rivers of London» Бена Ааронович.
Последовательность одинаковая для любой книги; отличаются только
пути и имена серии.

### Шаг 0 (по желанию): извлечь книгу из антологии

Если исходный EPUB — сборник нескольких книг в одном файле
(антология, собрание, «1-9 Collection»), нужно достать нужную книгу
отдельным файлом:

```bash
# Посмотреть, что внутри
python tools/split_epub.py path/to/omnibus.epub --list

# Извлечь книгу N (например, 4)
python tools/split_epub.py path/to/omnibus.epub --book 4
# → books/extracted/<book-slug>-<author>.epub
```

Если книга уже в отдельном EPUB — пропустить этот шаг.

### Шаг 1: извлечь словарь книги

Словарь — это список имён, мест, заклинаний и терминов с
предложенными переводами. Нужен для единообразия на протяжении
книги и серии.

Для первой книги серии — без `--series`:

```bash
btrans glossary extract books/extracted/rivers-of-london-ben-aaronovitch.epub
```

Результат: `work/<book-slug>/glossary.json`.
Время: 1–3 минуты. Стоимость: около $0.5–0.8 на книгу объёмом ~100 тысяч слов
(Claude Sonnet 4.6).

**Для второй и последующих книг серии** — с `--series`, чтобы модель
не придумывала новые переводы для уже известных терминов:

```bash
btrans glossary extract books/extracted/broken-homes-ben-aaronovitch.epub \
  --series rivers-of-london
```

**Для отдельной книги** (одна книга, серии нет или пока не нужна) —
команда та же, без `--series`:

```bash
btrans glossary extract path/to/book.epub
```

Шаги 3 и 4 (`series init` / `promote`) для отдельной книги не
нужны — смотрите сценарий 5б ниже.

### Шаг 2: вручную проверить словарь

Открыть `work/<book-slug>/glossary.json` в редакторе. Смотреть и
править в первую очередь записи с `"type": "person"` — ошибки в
именах персонажей самые заметные в тексте. Места и заклинания
обычно модель переводит разумно, и их можно просто пробежать глазами.

Для записей, которые вы подтвердили (или поправили и согласны) —
выставить `"approved_by_human": true`. Только такие записи
пойдут в серию на следующем шаге (`promote` по умолчанию берёт
только подтверждённые).

Время: 10–15 минут для ~100–150 записей.

Если словарь совершенно не устраивает — можно перегенерировать с более
строгим указанием: поправить `prompts/glossary_extract.md`, поднять
`version:` в заголовке файла, запустить `btrans glossary extract …`
ещё раз (кэш сбросится по версии указания, будет реальный
вызов языковой модели, ~$0.60).

### Шаг 3 (один раз на серию): инициализировать серию

Нужен, если книга — часть серии и вы планируете переводить
продолжения. Для отдельной книги пропустить: вместо этого на шаге 5
использовать `--glossary work/<book-slug>/glossary.json`.

Серия — это хранилище канонических терминов, общих для всех книг серии.
Создаётся один раз, потом переиспользуется.

```bash
btrans series init rivers-of-london \
  --title "Rivers of London" \
  --author "Ben Aaronovitch"
```

Создаёт `work/<slug>-series/series.glossary.json` (пустой).

### Шаг 4: перенести подтверждённые термины в серию (`promote`)

```bash
btrans glossary promote work/rivers-of-london \
  --series rivers-of-london
```

Что происходит:
- Берутся все записи с `approved_by_human: true` из
  `work/rivers-of-london/glossary.json`.
- Добавляются в словарь серии, дубликаты по полю `original` убираются.
- Если запись уже в серии с **другим** переводом — попадает в
  `conflicts`, вариант серии сохраняется, вариант книги показан
  для проверки.
- `--all` обходит фильтр по подтверждённым (осторожно).

После этого все последующие книги серии будут переводиться с
учётом этих канонических терминов.

### Шаг 5: перевод EPUB

Дальше — два сценария: книга внутри серии (используем канонический
словарь серии) и отдельная книга (используем её собственный
словарь либо вовсе без словаря).

#### 5а. Книга внутри серии (рекомендуемый путь)

```bash
btrans translate books/extracted/broken-homes-ben-aaronovitch.epub \
  --series rivers-of-london \
  -j 8
```

#### 5б. Отдельная книга со своим словарём

Если переводим одну книгу вне серии (или хочется прогнать пробный
перевод до `series init` / `promote`), используем `--glossary` и
передаём путь к `glossary.json`, полученному на шаге 1:

```bash
btrans translate path/to/book.epub \
  --glossary work/<book-slug>/glossary.json \
  -j 8
```

Что важно знать:

- `--series` и `--glossary` взаимоисключающие. Указывать нужно одно.
- При `--glossary` берутся **все** записи файла (поле
  `approved_by_human` не фильтрует — оператор явно указал файл, это
  и есть согласие). Если нужна строгая дисциплина подтверждений — правьте
  файл вручную или идите через `series promote`.
- Внутренне словарь приводится к тому же формату, что и серийный,
  указания и кэш работают одинаково.

#### 5в. Без словаря вообще

Если нужно быстро посмотреть, что выдаёт модель без каких-либо
канонических переводов — просто не указывать ни `--series`, ни
`--glossary`. Будет жёлтое предупреждение; перевод пройдёт, но
имена и термины модель выберет сама и может путаться от фрагмента
к фрагменту.

```bash
btrans translate path/to/book.epub -j 8
```

Не для чистового результата. Полезно только для прикидки.

#### Что делает translate под капотом

- Читает EPUB с сохранением деревьев разметки (lxml) всех документов
  (не плоский текст — чтобы вернуть теги обратно).
- Разбивает главы на фрагменты по ~2000 слов с перекрытием в 1 абзац.
- Для каждого фрагмента — обращается к Claude Sonnet 4.6 через настроенный
  text-провайдер с указанием, словарём и контекстом перекрытия.
- Работает параллельно по `-j` потоков.
- Переведённые фрагменты разметки вставляются обратно в дерево главы,
  пространства имён (namespace) сохраняются.
- **Оценка (judge)** (если не `--no-judge`): Haiku 4.5 оценивает каждый фрагмент
  по шкале 1–5 (точность, естественность, соответствие словарю, стиль, разметка).
- **Рефлексия (reflect)** (если не `--no-reflect`): фрагменты с оценкой ≤ 2
  проходят рефлексию по методу Andrew Ng — критика → повторный
  перевод с учётом замечаний. Исходный перевод сохраняется,
  улучшенный записывается как отдельный этап.

  Порог 2 выбран замером по трём полосам оценок, каждая против собственного
  контроля по шуму (тот же текст, оценённый дважды). В замечаниях на фрагмент:

  | было | рефлексия | шум | чистый эффект |
  |------|----------:|----:|---------------|
  | ★2 | −1,38 | −0,50 | **−0,88 — чинит** |
  | ★3 | −0,13 | +0,13 | −0,26 — вничью |
  | ★5 | +0,92 | +0,25 | **+0,67 — ломает** |

  На плохом фрагменте рефлексия снимает больше дефектов, чем все остальные
  стадии вместе (53 процитированных из 55 против 24). На хорошем — портит:
  она правит 87% абзацев независимо от того, есть ли что править.
- **Корректура (proofread)** (если не `--no-proofread`): Haiku 4.5 исправляет
  грамматику, пунктуацию и опечатки. Не трогает стиль.
- **Стилистика (style)** (если не `--no-style`): Sonnet 4.6 убирает кальки,
  канцелярит, улучшает авторский голос. Не меняет смысл.
- **Сверка (verify)** (если не `--no-verify`): Sonnet 4.6 сверяет перевод
  с оригиналом — ищет пропуски, искажения, нарушения словаря.
- Собирается новый EPUB: `books/extracted/<slug>-ru.epub` рядом с
  оригиналом (путь можно переопределить через `--out`).
- **Читательские сноски** вставляются, если в конфиге `reader_notes.enabled:
  true` и передан `--series` или `--glossary`. ⚠️ Шипящиеся конфиги
  (`configs/default.yaml`, `configs/kiro-gateway.yaml.example`) ставят
  `enabled: false` — включите флагом `--notes` или правкой конфига.
  Принудительно отключить: `--no-notes`.
- **Перевод обложки** (opt-in, платно): флаг `--cover` запускает
  image-провайдер после сборки EPUB. По умолчанию выключен.
  Standalone-команды `btrans cover translate` / `btrans assemble --notes`
  остаются доступны для точечной работы.

Время на ~115 тысяч слов / 102 фрагмента: около 50 минут при `-j 8`
(перевод ~16 мин + оценка ~0.5 мин + корректура ~8 мин +
стилистика ~13 мин + сверка ~13 мин).
Стоимость: ~$20–25 на книгу объёмом ~115 тысяч слов (полный конвейер со словарём).
Разбивка по моделям (реальный прогон «Shroud», 102 фрагмента):
- Claude Sonnet 4.6: ~$21 (словарь + перевод + стилистика + сверка)
- Claude Haiku 4.5: ~$3 (оценка + корректура)
- Итого: ~$24
Для книги объёмом ~60 тысяч слов / 60 фрагментов — пропорционально ~$12–14.

Повторный запуск той же команды — мгновенно из кэша в базе данных SQLite
(`work/<book-slug>/cache.sqlite`), языковая модель не вызывается.

Частые флаги:

```bash
# Предпросмотр первых N фрагментов (для быстрой проверки)
btrans translate ... --limit-chunks 7 --out preview.epub

# Свой путь для финального EPUB
btrans translate ... --out books/extracted/custom-ru.epub

# Переопределить модель (например, на Haiku для экономии)
btrans translate ... --model anthropic/claude-haiku-4.5

# Только перевод, без оценки и рефлексии
btrans translate ... --no-judge

# Оценка для статистики, но без рефлексии
btrans translate ... --no-reflect

# Рефлексия для всех фрагментов (не только плохих)
btrans translate ... --reflect-all

# Порог рефлексии: переделывать фрагменты с оценкой ≤ 2 (вместо ≤ 3)
btrans translate ... --reflect-threshold 2

# Пропустить отдельные проходы постобработки
btrans translate ... --no-proofread
btrans translate ... --no-style
btrans translate ... --no-verify

# Только перевод + оценка + рефлексия, без постобработки
btrans translate ... --no-proofread --no-style --no-verify
```

### Шаг 6: открыть готовый EPUB

Итог: `books/extracted/<slug>-ru.epub`. Открываем в Calibre,
Apple Books, Kindle (конвертация через Calibre) — любая читалка,
понимающая формат EPUB.

### Шаг 7 (по желанию): перевести или заменить обложку

Переведённый EPUB сохраняет оригинальную обложку с английским текстом.
Если хочется обложку на русском — есть два способа.

#### Извлечь обложку в файл

Полезно, чтобы посмотреть текущую обложку или использовать как основу
для ручной обработки:

```bash
# Автоматическое имя и расширение
btrans cover extract books/extracted/broken-homes-ru.epub
# → broken-homes-ru-cover.jpg

# Указать путь вручную
btrans cover extract books/extracted/broken-homes-ru.epub --out covers/original.png
```

Формат файла определяется из метаданных EPUB (JPEG, PNG, WebP и т.д.).

#### Способ А: заменить на свою картинку

Если у вас уже есть готовая обложка (нарисовали сами, нашли, заказали):

```bash
btrans cover replace books/extracted/broken-homes-ru.epub \
  --image my-russian-cover.jpg
```

Результат: `books/extracted/broken-homes-ru-cover.epub` с новой обложкой.

#### Способ Б: перевести текст на обложке с помощью ИИ

Модель получает оригинальную обложку и переводит весь видимый текст
на указанный язык. Работает через настроенный image-провайдер
(по умолчанию OpenRouter).

```bash
# Минимальный вариант — модель сама переведёт всё что найдёт
btrans cover translate books/extracted/broken-homes-ru.epub \
  --target-lang Russian

# С указанием конкретного перевода названия
btrans cover translate books/extracted/broken-homes-ru.epub \
  --target-lang Russian --title "Сломанные дома"

# С именем автора и конкретной моделью
btrans cover translate books/extracted/broken-homes-ru.epub \
  --target-lang Russian \
  --title "Сломанные дома" \
  --author "Бен Ааронович" \
  --model openai/gpt-5.4-image-2
```

**Параметр `--target-lang` обязателен** — модель должна знать, на какой
язык переводить.

**Параметр `--title` необязателен:**
- Если указан — модель использует именно этот текст как название книги.
  Полезно, когда у книги есть устоявшийся перевод названия.
- Если не указан — модель сама переведёт всё, что видит на обложке.
  Удобно для быстрого результата, но модель может перевести название
  буквально (не всегда удачно для художественной литературы).

**Что модель делает хорошо:**
- Сохраняет цветовую палитру и композицию обложки.
- Подбирает визуально похожий стиль шрифта (serif/sans-serif, bold/light).
- Сохраняет позиционирование текста.
- Переводит весь видимый текст (название, подзаголовок, серия, цитаты).

**Ограничения (честно):**
- Модель не знает точный шрифт оригинала — она подберёт визуально
  похожий, но не идентичный.
- Русский текст часто длиннее английского — модель может немного
  уменьшить размер шрифта, чтобы текст поместился.
- Результат не будет pixel-perfect копией оригинала с другим текстом —
  это скорее «профессиональная адаптация».
- Для сложных обложек с декоративными шрифтами или текстом,
  вписанным в иллюстрацию, результат может быть неидеальным.
  В таких случаях лучше использовать способ А.

**Доступные модели (через image-провайдер):**

| Модель | Флаг `--model` | Цена | Скорость | Когда использовать |
|--------|---------------|------|----------|-------------------|
| Nano Banana 2 (по умолчанию) | `google/gemini-3.1-flash-image-preview` | ~$0.03 | ~10 сек | Большинство обложек |
| GPT-5.4 Image 2 | `openai/gpt-5.4-image-2` | ~$0.15 | ~40 сек | Сложные обложки, лучшее качество |

**Дополнительные параметры:**
- `--aspect-ratio` — соотношение сторон (по умолчанию `2:3`, стандарт для книг).
- `--image-size` — разрешение: `1K` (по умолчанию), `2K`, `4K`.
- `--out` — путь для результата.

## Полезные проверки по ходу

### Статус перевода книги

```bash
# Обзор: фрагменты, этапы, стоимость, оценки
btrans status work/broken-homes/

# Таблица оценок
btrans status work/broken-homes/ --scores

# Только плохие фрагменты (оценка < 3)
btrans status work/broken-homes/ --scores --below 3

# Какой этап будет использован при сборке каждого фрагмента
btrans status work/broken-homes/ --assembly-map

# Сравнить перевод и рефлексию для конкретного фрагмента
btrans status work/broken-homes/ --diff ch03_c02 --stages translate,reflect
```

### Оценка и рефлексия отдельно от перевода

Если перевод уже в кэше и хочется прогнать оценку или рефлексию
отдельно (например, после правки указания):

```bash
# Оценить все переведённые фрагменты
btrans judge books/extracted/broken-homes-ben-aaronovitch.epub \
  --series rivers-of-london -j 4

# Рефлексия для фрагментов с оценкой ≤ 3
btrans reflect books/extracted/broken-homes-ben-aaronovitch.epub \
  --series rivers-of-london

# Рефлексия для всех фрагментов (независимо от оценки)
btrans reflect ... --all

# Рефлексия с другим порогом
btrans reflect ... --threshold 2
```

### Корректура / Стилистика / Сверка отдельно от перевода

Каждый проход можно запустить отдельно. Каждый берёт вход из
предыдущего этапа по цепочке (сверка читает стилистику, стилистика читает
корректуру, корректура читает рефлексию или перевод):

```bash
# Корректура: грамматика, пунктуация, опечатки (Haiku 4.5)
btrans proofread books/extracted/broken-homes-ben-aaronovitch.epub \
  --series rivers-of-london -j 8

# Стилистика: кальки, канцелярит, авторский голос (Sonnet 4.6)
btrans style books/extracted/broken-homes-ben-aaronovitch.epub \
  --series rivers-of-london -j 4

# Сверка: сравнение с оригиналом, пропуски, искажения (Sonnet 4.6)
btrans verify books/extracted/broken-homes-ben-aaronovitch.epub \
  --series rivers-of-london -j 4
```

Результаты хранятся как отдельные этапы в кэше. Ничего не
перезаписывается — можно откатить через `btrans prefer`.

### Точечная починка замечаний оценщика (`repair`)

Три прохода выше переписывают текст целиком и могут задеть то, что было в
порядке. Починка работает иначе: она берёт замечания, которые оценщик уже
сформулировал, и меняет **только процитированную фразу**, не трогая остальной
абзац.

Требуется пройденная оценка (`btrans judge`) — без неё чинить нечего.

```bash
# Посмотреть, что было бы предложено, ничего не вызывая и не записывая
btrans repair books/extracted/broken-homes-ben-aaronovitch.epub \
  --series rivers-of-london --dry-run

# Применить
btrans repair books/extracted/broken-homes-ben-aaronovitch.epub \
  --series rivers-of-london
```

Как это устроено. Каждое замечание разбирается в тройку «абзац, что заменить,
на что». Берутся только те, где процитированная фраза встречается в названном
абзаце **ровно один раз** — иначе непонятно, что именно менять. Дальше по
каждому кандидату модель, у которой на руках оригинал, решает, сохраняется ли
смысл. Отклонённое остаётся как было: неверная правка попадает в напечатанную
книгу, пропущенная — нет. Кандидат, по которому вердикта не пришло, считается
отклонённым — молчание не согласие.

Категории замечаний задаются в конфигурации (`repair.categories`) или ключом
`--categories`. По умолчанию включены `grammar`, `markup` и `accuracy` — те, где
исправление сводится к подстановке.

Этот список получен замером, а не выбран из общих соображений. На книге «Bear
Head» через привратника прошло 36 кандидатов, и доля отказов оказалась такой:

| категория | кандидатов | принято | отклонено |
|-----------|-----------:|--------:|----------:|
| `grammar` | 11 | 8 | 3 (27%) |
| `accuracy` | 20 | 13 | 7 (35%) |
| `glossary` | 5 | 1 | **4 (80%)** |

`accuracy` ведёт себя как грамматика и несёт больше всего дефектов, поэтому
включена. `glossary` убрана: её замечания чаще суждение — переставить имя
персонажа, заменить один придуманный термин другим, — а не подстановка. Для
отдельного прогона её можно вернуть ключом `--categories`.

`naturalness` и `register` не включаются вовсе: вкусовые правки автоматика
делает хуже, чем не делает.

> ⚠️ Починка не запустится, если `chunker.target_words` в конфигурации не
> совпадает с тем, при котором книга переводилась: границы фрагментов сдвинутся
> и накопленный кэш не состыкуется. Это же значит, что **починить нынешнюю
> книгу и перевести её заново с другим размером фрагмента — взаимоисключающие
> вещи.**

### Управление сборкой (prefer / assemble)

```bash
# Откатить рефлексию для конкретного фрагмента (вернуть первый перевод)
btrans prefer ch03_c02 translate --reason "рефлексия ухудшила диалог"

# Выбрать вариант рефлексии для фрагмента (если цепочка не та)
btrans prefer ch12_c01 reflect --reason "рефлексия лучше"

# Выбрать вариант корректуры (до стилистики)
btrans prefer ch05_c01 proofread --reason "стилистика испортила диалог"

# Сбросить предпочтение (вернуться к цепочке по умолчанию)
btrans prefer ch03_c02 --reset

# Собрать EPUB из конкретного этапа (игнорируя цепочку)
btrans assemble work/broken-homes/ --from translate --epub book.epub --out first-pass.epub
btrans assemble work/broken-homes/ --from reflect --epub book.epub --out reflected.epub
btrans assemble work/broken-homes/ --from proofread --epub book.epub --out proofread.epub
btrans assemble work/broken-homes/ --from style --epub book.epub --out styled.epub
```

Цепочка этапов при сборке: `translate` → `reflect` → `proofread` → `style` →
`verify` → `repair`. Берётся последний доступный, поэтому починка, если она
проходила, побеждает сверку.

### Читательские сноски из словаря (reader notes)

При сборке EPUB можно автоматически добавить подстрочные сноски
(EPUB footnotes) для терминов из словаря. Сноски формируются из
поля `notes` записей словаря — никаких вызовов языковой модели,
чисто детерминистическая пост-обработка.

**Зачем:** русскому читателю британского криминально-мистического
романа непонятны без контекста полицейские аббревиатуры (DCI, TSG),
латинские заклинания (vestigium, forma), отсылки к поп-культуре.
Официальные переводы решают это сносками — у нас та же информация
уже есть в словаре.

**Как работает:**
1. Фильтруются записи словаря по типу (по умолчанию `concept` и `term`)
   и наличию поля `notes`.
2. Для каждой главы (в порядке spine) ищется `translation` в тексте.
3. Первое вхождение (по scope) оборачивается в EPUB footnote-ref,
   текст `notes` добавляется как `<aside epub:type="footnote">`.

**Важно про `--epub`:** это исходный (английский) EPUB, из которого
берётся структура и вёрстка. Переведённый текст подставляется из кэша
(`work/<slug>/cache.sqlite`). Результат записывается в `--out` или
рядом с оригиналом с суффиксом `-ru`. Если файл с суффиксом `-ru` уже
существует (например, от предыдущего `translate`) — он будет
перезаписан без предупреждения. Чтобы сохранить оба варианта,
используйте `--out` с другим именем.

**Использование:**

```bash
# Сборка с читательскими сносками (книга в серии)
btrans assemble work/broken-homes/ \
  --epub books/extracted/broken-homes-ben-aaronovitch.epub \
  --notes --series rivers-of-london

# Сборка с читательскими сносками (отдельная книга)
btrans assemble work/broken-homes/ \
  --epub books/extracted/broken-homes-ben-aaronovitch.epub \
  --notes --glossary work/broken-homes/glossary.json

# Указать типы терминов для аннотирования
btrans assemble work/broken-homes/ \
  --epub books/extracted/broken-homes-ben-aaronovitch.epub \
  --notes --series rivers-of-london \
  --note-types concept,term,place

# Без сносок (явно)
btrans assemble work/broken-homes/ \
  --epub books/extracted/broken-homes-ben-aaronovitch.epub \
  --no-notes --series rivers-of-london
```

**Настройки** (`configs/default.yaml`):

```yaml
reader_notes:
  enabled: false          # в шипящихся конфигах выключено; поставьте true, чтобы включить
  types: [concept, term]  # какие типы терминов аннотировать
  scope: first-in-book    # first-in-book | first-in-chapter | all
```

> ⚠️ **Про дефолт:** в коде `enabled` по умолчанию `true`
> ([models.py](src/booktranslator/models.py)), но шипящиеся конфиги
> (`configs/default.yaml`, `configs/kiro-gateway.yaml.example`) переопределяют
> его в `false` — то есть с ними сноски выключены, пока вы не поставите
> `enabled: true` или не передадите `--notes`. Флаг `--notes/--no-notes`
> перекрывает конфиг и работает и в `assemble`, и в `translate`. Если глоссарий
> не передан (`--series`/`--glossary`) — сноски пропускаются с предупреждением.

**Особенности:**
- Для коротких терминов (≤4 символов) — строгое совпадение по границам
  слова (чтобы «art» не совпало с «article»).
- Для длинных терминов — допускаются суффиксы (русская морфология:
  «вестигиум» совпадёт с «вестигиуме»).
- Сноски не вставляются внутрь существующих ссылок (`<a>`) или
  уже размеченных сносок — XHTML остаётся валидным.
- `--notes` и `--no-notes` перекрывают значение из конфига.
- `--series` и `--glossary` взаимоисключающие (как в `translate`).
- Сноски встроены в `btrans translate` (передайте `--series`/`--glossary`).
  `btrans assemble --notes` остаётся для точечной сборки из кэша.

**Флаги обложки в `btrans translate`:**

```bash
# Перевести обложку после сборки (opt-in)
btrans translate book.epub --series rivers-of-london --cover

# С явным переводом названия и имени автора
btrans translate book.epub --series rivers-of-london \
  --cover --cover-title "Реки Лондона" --cover-author "Бен Ааронович"

# Другой язык или модель
btrans translate book.epub --series rivers-of-london \
  --cover --cover-target-lang German --cover-model openai/gpt-5.4-image-2
```

Если image-провайдер недоступен или вернул ошибку — `translate` завершается
успешно, переведённый EPUB сохраняется, обложка пропускается с предупреждением.

### Сколько реально кириллицы в собранном EPUB

Грубая проверка, что все главы переведены на русский:

```bash
.venv/bin/python - << 'EOF'
import zipfile, re
from pathlib import Path
p = Path('books/extracted/broken-homes-ben-aaronovitch-ru.epub')
with zipfile.ZipFile(p) as z:
    for name in sorted(z.namelist()):
        if not (name.endswith('.xhtml') or name.endswith('.html')):
            continue
        data = z.read(name).decode('utf-8', errors='replace')
        cyr = len(re.findall(r'[а-яА-ЯёЁ]', data))
        lat = len(re.findall(r'[a-zA-Z]', data))
        if cyr + lat > 100:
            pct = 100 * cyr / (cyr + lat)
            print(f'{name:30s} cyr={cyr:>6} lat={lat:>6} ru={pct:5.1f}%')
EOF
```

Ожидаем 80–90% кириллицы в главах, 0% в `titlepage.xhtml`
(имя автора латиницей).

## Решение проблем

### «returned no content» — модель ничего не ответила

Ответ пришёл пустым. На kiro-gateway причина почти всегда одна: подделанное
размышление съело весь бюджет ответа, и на сам ответ места не осталось.
Пустота **не записывается в кэш**, и повторных попыток не делается — повторять
такой запрос бесполезно.

Что проверить, по порядку:

1. **`FAKE_REASONING=false` в настройках шлюза.** Это главная причина. Без этого
   перевод через шлюз не работает ни при каком размере фрагмента.
2. **Размер фрагмента.** Уменьшить `chunker.target_words` — для шлюза
   рекомендуется 1200.
3. **`reasoning_effort` в заголовке указания** — понизить или поставить `none`.

Совет «увеличить `max_tokens`» помогает на OpenRouter, но **не на шлюзе**: этот
параметр туда вообще не передаётся, он лишь задаёт долю бюджета под размышление.

Подробности и замеры — в разделе «Ограничение шлюза на длину ответа».

### В журнале: «past the … warning threshold»

Ответ подошёл к границе, заданной в `max_response_bytes`. Пока это только
предупреждение — ответ пришёл целиком. Но следующий, чуть более длинный
фрагмент может уже не поместиться. Стоит уменьшить `chunker.target_words`
заранее, не дожидаясь пустых ответов.

### Фрагмент не прошёл: «Translated fragment is not well-formed XML»

Чаще всего — голый символ `&` в выводе модели (бренды типа «M&S», «AT&T»).
Исправление уже в `translator.py`: экранируем автоматически. Если снова
увидите — проверьте, что работаете на последней версии (`git log`
должен показывать коммит `fix: escape bare ampersands …`).

### Фрагмент не прошёл: «Expected N paragraphs, got M»

Модель склеила или разбила абзацы. Сейчас фрагмент помечается как
неудавшийся, перевод не записывается. При повторном запуске — повторная
попытка автоматическая (кэш не содержит неудавшихся фрагментов). Если фрагмент
стабильно не проходит — попробовать `--model anthropic/claude-haiku-4.5`
для этого конкретного прогона или поправить указание.

### Повторный запуск долгий, а должен быть из кэша

- Проверить, что `work/<book-slug>/cache.sqlite` на месте.
- Проверить, не менялись ли указания (версия в заголовке → ключ
  кэша).
- Проверить, не менялся ли словарь серии (его хэш входит в ключ).

### Ограничение частоты запросов (rate limit)

`-j 16` и выше — риск получить ошибку 429. Снизить до `-j 8` или `-j 4`. В
модуле обращения к модели (`provider.py`) стоит повторная попытка с нарастающей
задержкой (exponential backoff), но она не спасёт от жёсткого ограничения.
Актуально для любого провайдера (OpenRouter, kiro-gateway и т.д.).

### Глоссарий: «Книга, похоже, обрезана провайдером» (`TruncationError`)

Стадия `glossary` шлёт всю книгу одним запросом и проверяет маркеры в начале и
конце текста. Эта ошибка значит, что провайдер вернул не весь текст (типично для
kiro-gateway на большой книге). Решение: увести `glossary` на провайдер с большим
контекстом (OpenRouter, 200k) — см. «Почему глоссарий стоит увести на OpenRouter».
Словарь по неполному тексту намеренно **не сохраняется**.

### Глоссарий: «Model returned empty content»

Модель вернула пустой ответ — обычно потому, что на шлюзе включён extended
thinking и «размышления» съели весь бюджет вывода. Во всех промптах текстовых
стадий стоит `reasoning_effort: none` именно для этого. Если ошибка возникает —
проверьте, что в `prompts/*.md` (особенно `glossary_extract.md`) в заголовке
есть `reasoning_effort: none`, и что провайдер стадии его принимает.

### Забыл `--series` при `glossary extract` — как перенести словарь в серию

Перегенерировать **не нужно**. Флаг `--series` при `glossary extract` — это лишь
оптимизация для 2-й и последующих книг: он подсовывает модели уже известные
термины серии, чтобы она не извлекала их заново. Для **первой** книги серии его
не указывают вовсе. Сам словарь от наличия/отсутствия флага «серийным» не
становится — перенос в серию делается отдельной командой `promote`.

Уже сгенерированный `work/<slug>/glossary.json` переносится в серию в три шага:

```bash
# 1. Создать серию (один раз)
btrans series init bear-head \
  --title "Bear Head" \
  --author "Adrian Tchaikovsky"

# 2. (в редакторе) проставить "approved_by_human": true на проверенных записях
#    в work/bear-head/glossary.json — promote по умолчанию берёт только их.

# 3. Перенести в серию
btrans glossary promote work/bear-head --series bear-head
#    --all — перенести ВСЕ записи без фильтра по approved_by_human
```

Даже если серия уже существовала и флаг был забыт — `promote` дедуплицирует
записи по полю `original`, а расхождения переводов складывает в `conflicts`
(вариант серии сохраняется, вариант книги показывается для проверки). Поэтому
повторный вызов модели не требуется ни в одном из случаев.

Подробнее про серии и `promote` — в разделе «Перевод книги: пошагово»,
шаги 3–4.

- **Перевод с венгерского на русский** — версия 1.2.

- **Снятие защиты от копирования (DRM)** — и не будем. Используйте Calibre + DeDRM отдельно
  на легально приобретённых книгах.
- **Вёрстка PDF для типографии** — вне задач проекта. На выходе только EPUB.
